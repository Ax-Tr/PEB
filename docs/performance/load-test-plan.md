# Load-Test Plan (Sprint 17)

Tooling: [k6](https://k6.io) (scriptable, CI-friendly, good percentile reporting). Scripts live in
`docs/performance/k6/`. Runs target a **deployed** environment via the gateway base URL — they are
not executable in this repo sandbox (no running cluster), but are ready to run in staging/CI.

## Scenarios

| Script | Exercises | Why it matters |
|---|---|---|
| `k6/read-list.js` | Keyset-paginated list endpoints (invoices, suggestions, DSRs) | Proves list latency stays flat as data grows (keyset vs offset). |
| `k6/analytics-dashboard.js` | `/api/v1/analytics/pnl`, `/cashflow`, `/receivables-aging` | Verifies the < 3 s P95 dashboard SLO and that analytics never touches OLTP. |
| `k6/write-invoice.js` | Create invoice → collect payment (write path) | Write P95 SLO + outbox/Kafka throughput under load. |
| `k6/mixed-peak.js` | 80/20 read/write blend ramped to 10k VUs | Finds the stress knee; drives autoscaling. |

## Method

1. **Ramp profile** per `slos.md` (baseline → nominal → peak → stress → soak). k6 `stages` implement
   the ramp; `thresholds` encode the SLOs so a run fails automatically when a P95 is breached.
2. **Warm up** caches and JIT for 2 min before measuring.
3. **Isolate tenants**: use ≥ 50 synthetic tenants so tenant-scoped indexes/caches are exercised
   realistically (not one hot tenant).
4. **Observe** during the run: gateway P50/P95/P99, error rate, Kafka consumer lag, DB pool
   utilisation & slow-query log, pod CPU/mem, GC pauses.

## Example k6 thresholds (encoded in scripts)

```js
export const options = {
  scenarios: { /* ramping-vus stages per slos.md */ },
  thresholds: {
    'http_req_duration{kind:read_list}': ['p(95)<250'],
    'http_req_duration{kind:analytics}': ['p(95)<3000'],
    'http_req_duration{kind:write}':     ['p(95)<350'],
    http_req_failed:                     ['rate<0.001'],
  },
};
```

## Pass criteria (DoD)

- Every latency class meets its P95 SLO within its error budget at the **peak** stage.
- Kafka consumer lag < 5 s at peak; analytics freshness stays FRESH.
- No DB query > 200 ms P95 on hot paths; connection pool < 80%.
- 4 h soak shows no memory leak / GC degradation.
- The run's report (auto-generated by k6 `handleSummary`) is attached to the sprint DoD as the
  **load-test report**.

## Deliverables

- `k6/*.js` scripts (in this folder) — runnable against `BASE_URL` + a bearer token.
- A results report per environment (staging sign-off, then production readiness in Sprint 18).
